# 0002 — 训练会话通知采用免前台服务方案，引入逃课状态

「开始训练」后需要在状态栏常驻挂着当天打卡进度的可操作通知。我们决定**不使用前台服务**：常驻通知 + 进程内观察者（app 内打卡/调重量实时刷新）+ 广播接收器（通知按钮打卡时写库并刷新）。被否掉的方案是前台服务保活——它能在进程死后维持"完美实时"，但状态只在有打卡行为时才会变化（打卡行为本身就会唤醒进程并刷新），为不存在的更新场景常驻耗电不值；且需 FOREGROUND_SERVICE 权限与 specialUse 类型声明，与本项目极简风格冲突。代价是进程被杀后通知静止展示旧状态，任意交互即刷新——自愈式陈旧可接受。

同时引入**逃课**状态（`day_plans.skipped`）：通知 [逃了] = 结束会话并标记当天逃课，主页显示逃课卡片、可反悔（清除标记后可重新开始训练），导出周计划标注。已打卡内容保留（练了就是练了）。逃课是主动放弃的显式标记，不是完成度统计（与"不做统计"原则不冲突）。

## Consequences

- 进程被杀期间通知不会自行更新（没有进程可更新它）；接收器在每次交互时校验会话行仍存在，陈旧通知的按钮不会误写数据。
- 隔天残留会话在 app 启动时自动清理（删行 + 撤通知）。
- 会话行（`workout_session`）是常驻通知的权威来源：行存在 = 会话进行中；通知只是它的视图。
